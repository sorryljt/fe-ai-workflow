# ANALYZE — 需求分析与任务拆分

## 概述

将已确认的设计文档（`design.md`）或 PRD，分解为粒度合适的任务列表（`tasks.md`）。
每个任务对应一个完整的 TDD 红绿重构循环，约 2-5 分钟完成。

## 触发条件

以下任一情况触发本 Skill：
- 用户输入 `/viktor:plan` 命令
- BRAINSTORM 节点完成且用户已确认 `design.md`
- 用户提供了 PRD 文档要求直接拆分

## 输入规范

支持以下格式作为输入：
- `docs/specs/YYYY-MM-DD--design.md`（brainstorming 产物，推荐）
- Markdown 格式的 PRD 文档
- Notion 导出的 Markdown
- 用户直接粘贴的需求文本

## 执行步骤

### 前置步骤：会话感知冷启动检测

检查当前对话历史中，是否存在 **BRAINSTORM 节点刚完成的信号**（导航卡中含有指向 `/viktor:plan` 的 `▶` 提示）：

**在流模式（检测到信号）**：
- 直接使用对话中 BRAINSTORM 刚确认的 spec 文件，跳过以下扫描步骤
- 继续执行第 1 步

**冷启动模式（未检测到信号）**：

1. 扫描 `docs/specs/` 下所有 `*.md` 文件：
   - **有多个文件** → 列出让用户选择输入来源：
     ```
     找到以下设计文档：

     A. 2026-05-19 · session-aware-confirmation
     B. 2026-05-18 · contract-node

     请选择要拆分的设计文档（输入 A / B / ...）：
     ```
   - **只有一个文件** → 直接告知「将使用 [文件名] 作为输入」，无需选择
   - **没有任何文件** → 提示：「未找到设计文档。请执行 `/viktor:think <需求描述>` 先完成需求设计，或直接粘贴 PRD 文本。」

2. 检查 `docs/plans/` 下是否已有同功能的 tasks.md：
   - **存在相近文件** → 提示：「检测到已有任务文件 [文件名]，是要覆盖还是新建一份？(覆盖/新建)」
   - **不存在** → 直接继续

### 第 1 步：解析文档结构

读取输入文档，提取以下信息并逐一列举：

**功能点列表**：
```
功能 F001：[名称] - [一句话描述]
功能 F002：[名称] - [一句话描述]
```

**验收标准**：每个功能的完成判断标准（是否可测试？如果模糊，提示用户补充）

**边界条件**：
- 异常场景（网络错误、权限不足、空状态）
- 输入边界（字段长度限制、格式要求）

**技术约束**：性能要求、SSR/CSR 选择、浏览器兼容性

检查：每个功能的验收标准是否可测试？如果存在"用户体验良好"、"响应速度快"等模糊标准，停止并提示：
> "F00X 的验收标准 '[模糊标准]' 无法测试，请补充具体指标。"

### 第 2 步：识别技术依赖和风险点

**外部依赖**：
- 需要调用的 API 端点（确认是否已就绪）
- 第三方库（是否需要安装）

**内部依赖**：
- 依赖其他团队/模块尚未完成的接口
- 依赖已有组件的修改

**技术风险**（标注 `⚠️ 风险`）：
- 实现方式不确定，需要先调研或 spike
- 复杂度可能超出预期的任务
- 有性能风险的操作（大列表渲染、频繁请求）

### 第 3 步：拆解任务列表

**任务类型标注**：

| 类型标注 | 对应内容 | TDD 要求 |
|---------|---------|---------|
| `[utils]` | 工具函数 | 强制 TDD |
| `[hook]` | 自定义 Hook | 强制 TDD |
| `[component]` | React 组件 | 有交互时 TDD |
| `[api]` | API 路由 / Server Action | 强制 TDD |
| `[store]` | 状态管理（Zustand 等） | 强制 TDD |
| `[style]` | 纯样式 / 布局 | 无需 TDD |

**拆分粒度原则**：
- 每个任务 = 一个完整 TDD 红绿循环 = 约 2-5 分钟
- 每个任务有单一明确的输入/输出边界
- 依赖其他任务的内容单独成一个任务

**粒度示例对比**：

❌ 粒度太大（一个任务涉及多个文件和多种逻辑）：
```
T001: 实现用户认证功能
```

✅ 粒度合适（每条单一职责，2-5 分钟可完成）：
```
T001: [utils] validateEmail() - 邮箱格式验证
T002: [utils] validatePassword() - 密码强度校验
T003: [hook] useLoginForm() - 表单状态和校验逻辑
T004: [component] LoginForm - 渲染 + 用户交互
T005: [api] POST /api/auth/login - 服务端认证逻辑
T006: [style] LoginPage 布局样式
```

### 第 4 步：标注优先级和依赖关系

**优先级**：
- `P0`：核心路径，阻塞其他任务，必须最先完成
- `P1`：主要功能，完成后功能可用
- `P2`：优化/边缘场景，可延后处理

**依赖关系**：
- `depends: T001` — 依赖单个任务
- `depends: T001, T002` — 依赖多个任务
- 无标注 = 无依赖，可立即开始

**推荐执行顺序**：
1. 所有 `[utils]` 和 `[hook]`（无 UI 依赖，纯逻辑，最易 TDD）
2. `[api]` 和 `[store]`（数据层）
3. `[component]`（UI 层，依赖上述逻辑）
4. `[style]`（最后处理，无阻塞）

### 第 5 步：输出 tasks.md

按照下方模板生成任务列表，保存到：
`docs/plans/YYYY-MM-DD--<feature-name>--tasks.md`

执行：
```bash
git add docs/plans/
git commit -m "docs: add task breakdown for <feature-name>"
```

提示用户：
> "任务分解完成，共 N 个任务（P0: X 个，P1: Y 个，P2: Z 个）。
> 请确认粒度是否合适：每条任务是否能在约 5 分钟内完成一个 TDD 循环？
> 确认后参考下方导航卡选择下一步。"

### 第 6 步：评估是否需要 CONTRACT 节点，输出导航卡

根据任务列表的构成，判断是否建议生成类型合约：

**推荐规则**：

| 任务构成 | 推荐 |
|---|---|
| 含 `[api]` 类型任务 | ✅ 推荐 CONTRACT |
| 含 `[hook]` 或 `[store]` 类型任务 | ✅ 推荐 CONTRACT |
| 多个组件共享同一数据结构 | ✅ 推荐 CONTRACT |
| 涉及跨模块类型复用 | ✅ 强烈推荐 CONTRACT |
| 全部为 `[utils]` / `[style]` 类型 | ⏭ 建议跳过 |
| 任务总数 ≤ 3 且无 API 接口 | ⏭ 建议跳过 |

**导航卡（推荐走 CONTRACT 时）**：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✅ ANALYZE 已完成
📄 产物：docs/plans/YYYY-MM-DD--tasks.md（N 个任务）
──────────────────────────────
📋 检测到 [api] / [hook] / [store] 类型任务，建议先锁定类型合约

▶ 选项 A（推荐）：/viktor:contract  生成类型合约文件
▶ 选项 B：/viktor:code              跳过合约，直接开始 TDD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**导航卡（建议跳过 CONTRACT 时）**：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✅ ANALYZE 已完成
📄 产物：docs/plans/YYYY-MM-DD--tasks.md（N 个任务）
──────────────────────────────
💡 本次需求较简单，可直接进入 TDD

▶ 下一步（推荐）：/viktor:code      开始 TDD 实现
▶ 也可以：/viktor:contract          仍然生成类型合约
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 验证标准

tasks.md 合格的标志：
- [ ] 每个任务粒度约 2-5 分钟（一个 TDD 循环）
- [ ] 每个任务有明确的文件路径（实现 + 测试）
- [ ] 每个任务的验收标准可测试、可量化
- [ ] 每个任务的测试要点覆盖：正常路径、边界条件、异常处理
- [ ] 依赖关系已明确标注
- [ ] 风险点已识别并标注应对策略
- [ ] 任务总数合理（太少=粒度太大，太多=过度拆分）
