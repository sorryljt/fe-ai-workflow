# BRAINSTORM — 需求澄清与设计沉淀

## 概述

将模糊的需求或想法转化为结构化的设计文档（`design.md`）。
**核心原则：AI 主导推荐，用户纠偏。** 对有合理默认值的决策直接采用并在假设中声明；只对真正存在多方案权衡的关键分歧点提问，且一次性批量提出，最终一轮确认完成。
设计文档是后续所有工作的唯一事实来源（Single Source of Truth），未经确认不得开始实现。

## 触发条件

- 用户输入 `/viktor:think <需求描述>` 命令

## 执行步骤（严格按顺序，不可跳步）

### 第 1 步：探索项目上下文

在提问之前，先了解当前项目状态：

**情况 A — `docs/project-context.md` 存在**：直接读取，无需重新扫描。

**情况 B — `docs/project-context.md` 不存在**：
1. 告知用户：`"未检测到项目知识地图，正在自动扫描项目结构，完成后继续需求分析..."`
2. 执行 `skills/06-project-init/SKILL.md` 的第 1-4 步（扫描并生成 `docs/project-context.md`）
3. 保存文件后继续 BRAINSTORM 流程，无需用户干预

完成以上任一情况后，额外执行：
- 查看 `docs/specs/` 下已有的 design.md（避免重复）
- 检查 `references/react-nextjs-conventions.md` 中的相关规范

**目的**：避免提出项目已有答案的问题；确保推荐方案与现有架构一致；识别已有组件可复用的情况。

### 第 2 步：评估需求范围

判断需求规模，决定是否需要拆分：

- **小型**：单一组件或工具函数，一个 TDD 循环能完成 → 继续
- **中型**：多个组件/接口，需要多个 TDD 循环 → 继续，设计时标注依赖关系
- **大型**：涉及多个独立子系统（如认证 + 权限 + 用户管理）→ 拆分

如需拆分，提示：
> "此需求较大，涉及多个独立子系统，建议拆分为以下子项目分别走工作流：
> 1. [子项目 A]
> 2. [子项目 B]
> 请选择优先处理哪个？"

### 第 3 步：识别关键决策点，批量提问（最多 3 个）

**区分「需要问」和「直接推断」**：

| 情况 | 处理方式 |
|------|---------|
| 项目已有相同场景的解决方案 | 直接沿用，在假设中说明 |
| 技术栈已隐含选择（如用了 App Router） | 直接推断，在假设中说明 |
| 行业通用做法（如前端+服务端双重校验） | 直接采用，无需问 |
| 有多个方案且各有明显权衡，上下文无法推断 | **需要问** |
| 涉及只有用户知道的业务规则 | **需要问** |

**如有需要问的问题（最多 3 个），一次性批量提出**，多选题格式：

```
开始设计前有 [N] 个关键选择需要你决策：

1. 表单状态管理？
   A) useState（轻量，与项目现有方式一致）
   B) react-hook-form（功能完整，需引入依赖）

2. [问题 2，如有]
   A) ...  B) ...

请选择后我直接生成完整设计文档。
```

如果所有决策均可由上下文推断，**跳过本步**，直接进入第 4 步。

### 第 4 步：生成完整设计文档，声明假设

根据用户回答（如有）+ 项目上下文推断，**一次性生成完整设计文档**。

在文档开头插入「AI 假设声明」区块，列出所有自主推断的决策：

```markdown
> **设计假设**（以下判断来自项目上下文推断，如有不符请在确认时指出具体条目）：
> 1. 使用 useState 管理表单状态（项目未引入 react-hook-form）
> 2. 错误提示沿用项目现有 Toast 组件
> 3. 通过 fetch POST 到 /api/comments（与项目现有接口风格一致）
```

用户看到假设列表，**只需指出不符的点**，不需要逐一确认每条。

### 第 5 步：Spec 自审（展示之前内部执行）

生成文档后、展示之前，自检并修复：

- [ ] 无占位符（TBD / 待定 / TODO / [填写]）
- [ ] 无内部矛盾（如 A 部分说 Server Component，B 部分说 useState）
- [ ] 无歧义表述（"合适的时候"、"必要时"、"适当地"）
- [ ] 每个功能点有至少一条可测试的验收标准
- [ ] 假设声明覆盖了所有自主推断的决策

### 第 6 步：单轮确认

展示完整文档，提问：
> "设计文档已生成，请确认是否符合预期，或指出需要调整的具体章节。"

**收到反馈后的处理逻辑**：
- 「没问题 / 确认 / OK」→ 直接进入第 7 步
- 「第 X 部分需要改…」→ 只修改该章节，**无需整体重新确认**，修改完展示变更内容后直接进第 7 步
- 需要大幅调整 → 退回第 3 步重新提问（极少情况）

### 第 7 步：Commit 并输出导航卡

```bash
git add docs/specs/
git commit -m "docs: add design spec for <feature-name>"
```

输出导航卡（见末尾「导航卡」章节）。

## 设计文档模板

```markdown
# [功能名称] 设计文档

**日期**：YYYY-MM-DD
**状态**：已确认
**关联 PRD**：[链接，如有]

## 1. 背景

[描述此功能要解决的问题，为什么现在要做，业务价值是什么]

## 2. 目标

**要做的事**：
- [ ] [具体可验证的目标 1]
- [ ] [具体可验证的目标 2]

**不做的事（明确边界）**：
- [排除的功能 1 及原因]
- [排除的功能 2 及原因]

## 3. 方案对比

| 维度 | 方案 A | 方案 B |
|------|--------|--------|
| 性能 | ... | ... |
| 可维护性 | ... | ... |
| 开发成本 | ... | ... |
| SEO/SSR | ... | ... |

## 4. 选定方案

**选择方案 X**

原因：[具体的决策理由，说明为什么选这个而不是其他的]

## 5. 技术细节

### 5.1 技术选型

- 框架：Next.js 14 App Router
- 渲染策略：[Server Component / Client Component / 混合]
- 数据获取：[fetch + ISR / SWR / Server Action]
- 状态管理：[useState / Zustand / 无]
- 样式：[Tailwind CSS + cn()]

### 5.2 组件设计

```
页面组件树：
└── [PageName]Page（Server Component）
    ├── [FeatureName]List（Server Component，数据获取）
    │   └── [ItemName]Card（Client Component，交互）
    └── [ActionName]Button（Client Component，用户操作）
```

### 5.3 接口定义

```typescript
// 核心数据类型
interface [EntityName] {
  id: string
  // ...
}

// 组件 Props
interface [ComponentName]Props {
  // ...
}

// API 响应类型
interface [ApiName]Response {
  data: [EntityName][]
  total: number
}
```

### 5.4 数据流

[描述数据如何从数据源流向 UI：API → Server Component → Client Component → 用户]

## 6. 边界条件与错误处理

| 场景 | 触发条件 | 处理方式 | 用户提示 |
|------|---------|---------|---------|
| 加载中 | 数据请求进行中 | Skeleton 占位 | - |
| 空状态 | 列表为空 | 空状态插图 + 引导文案 | "暂无数据，[引导操作]" |
| 网络错误 | 请求超时/断网 | 错误提示 + 重试按钮 | "网络连接失败，请重试" |
| 服务器错误 | 5xx 响应 | 友好错误页 | "服务暂时不可用" |
| 权限不足 | 401/403 | 跳转登录页 | "请先登录" |

## 7. 验收标准

- [ ] [功能验收 1：可测试、可量化]
- [ ] [功能验收 2]
- [ ] 所有交互状态（loading/error/empty/success）有对应 UI 反馈
- [ ] 错误处理覆盖所有边界条件
- [ ] TypeScript 无类型错误
- [ ] 测试覆盖率 > 80%
```

## 反理由表

| 借口 | 反驳 |
|------|------|
| "需求很清楚，不需要 brainstorm" | 清楚是你的感受，design.md 是团队对齐的载体。即使 30 分钟的设计确认，也能省掉数小时的返工。 |
| "这是个小改动" | 小改动也可能有隐藏的边界条件或技术债务。design.md 可以很短，但必须存在。 |
| "先做出来再改" | 没有设计直接实现，等于在不看地图的情况下跑步，方向错了全部重来。 |
| "PRD 已经很详细了，直接 analyze" | PRD 是业务需求，design.md 是技术方案。两者关注点不同，都需要。 |
| "时间不够了" | 跳过 brainstorm 节省的 30 分钟，可能让整个 PR 返工 3 小时。 |

## Hard Gate

**用户未明确确认 `design.md` 之前，禁止调用 `/viktor:plan` 或 `/viktor:code`。**

## 验证标准

Brainstorming 成功完成的标志：
- [ ] `design.md` 已保存到 `docs/specs/` 并 committed
- [ ] 文档开头有「AI 假设声明」区块
- [ ] 文档中无任何占位符（TBD/待定/TODO）
- [ ] 文档中无歧义表述
- [ ] 每个功能点有至少一条可测试的验收标准
- [ ] 用户明确确认了文档内容
- [ ] 技术方案有明确的选择理由（包括为什么不选其他方案）
- [ ] 全程提问不超过 1 轮（3 个以内问题），确认不超过 1 轮
