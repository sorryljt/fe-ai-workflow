# ADR-005: 补全工作流完整性缺口——BRAINSTORM 冷启动、INIT 幂等化、digest 触发优化、references 变更检测

**日期**：2026-05-19
**状态**：已接受
**提出者**：Dawson
**关联需求**：工作流完整性补全（workflow-completeness-polish）

## 背景

通过 `/viktor:context` 快照分析，发现 v0.6.0 工作流存在 7 处可用性缺口：

1. **BRAINSTORM 无冷启动检测**：其余 5 个主流程节点在 v0.6.0（ADR-004）已实现会话感知冷启动，但作为入口的 BRAINSTORM 节点缺失。用户在新会话中运行 `/viktor:think` 时，若已有同功能的 spec 文件，可能静默覆盖历史设计文档。

2. **INIT 重复执行不安全感**：`/viktor:init` 文档和概述写"一次性扫描"，用户不清楚项目重构后能否再次执行，存在顾虑。实际上第 6 步（活文档骨架）已有"已存在则跳过"的逻辑，但未对用户可见。

3. **PRD 输入路径未明确**：`references/prd-input-template.md` 存在，但 BRAINSTORM Skill 从未显式引用。用户带完整 PRD 进来时，工作流对处理路径无指引。

4. **init vs think 入口对新用户不透明**：新项目用户不知道是先 `init` 再 `think`，还是 `think` 会自动处理。

5. **digest 建议条件（5 的倍数 ADR 数）过严**：每完成一个功能阶段都适合整合文档，但触发条件要求 ADR 数量为 5 的整数倍，实际使用中很少触发。

6. **references 变更无追溯机制**：`react-nextjs-conventions.md` 等规范文件更新后，没有机制提示相关 Skill 同步检查，可能导致规范与 Skill 行为悄然漂移。

7. **CONTRACT/REVIEW 冷启动单文件处理逻辑隐含**（来自 ADR-004 review NIT）：单文件时"直接使用"是隐含行为，未明文说明。

## 决策

### D1 — BRAINSTORM 冷启动：检测已有 spec，询问新建还是更新

**决策**：在 BRAINSTORM 执行步骤前，扫描 `docs/specs/` 下已有 `.md` 文件。若存在，列出文件列表，询问用户是"新建"还是"更新"已有文档。

**为什么不用"上游信号检测"（ADR-004 模式）**：BRAINSTORM 是整个工作流的入口，没有"上游节点"会产生指向它的导航卡信号。ADR-004 的检测模式需要上游节点产生的 `▶ /viktor:xxx` 信号，不适用于第一个节点。

**为什么选择"检测 spec 文件而非对话历史"**：spec 文件是持久化状态，跨会话可靠；对话历史对于入口节点无实质意义，因为每次都是新需求开始的地方。

**更新模式边界**：用户选择更新时，跳过第 1-3 步（探索/范围评估/提问），直接进入第 4 步（文档修改模式），修改完成后继续第 5-7 步（自审/确认/commit）。

### D2 — INIT 幂等化：A/B 两模式询问

**决策**：检测到 `project-context.md` 已存在时，询问用户：A（重新扫描更新）或 B（仅补全缺失骨架）。任何路径均不删除已有内容，骨架文件已存在时跳过。概述措辞从"一次性扫描"改为"扫描或更新"。

**为什么不静默选择**：重新扫描会覆盖 `project-context.md` 中用户可能手动补充的内容，应由用户决定；仅补骨架风险低，但明确询问有助于用户理解工具能力。

### D3 — DOCUMENT digest 选项：从条件触发改为固定导航卡

**决策**：移除"ADR 数量为 5 的倍数"条件判断。每次 DOCUMENT 完成后，导航卡固定包含一个 `💡` 非阻塞选项：`/viktor:digest`。

**为什么移除 5 的倍数条件**：这个条件来自"每完成一个大阶段约有 5 个 ADR"的经验估计，但实际项目节奏各异，且条件隐蔽（用户不知道为什么某次出现、某次不出现）。固定出现的非阻塞选项更透明，用户自行决定执行频率。

**为什么放在导航卡而非作为单独提示**：减少对话噪音——导航卡末尾的 `💡` 标记视觉权重低于 `▶`，用户可轻易忽略。

### D4 — DOCUMENT 新增 references 变更检测

**决策**：在 DOCUMENT 第 1 步工作流自身变更检测之后，新增 `references/` 变更检测。若有 references 文件变更，输出映射表（哪个文件 → 哪个 Skill 引用），提示用户逐一确认是否需要更新对应 Skill。非阻塞。

**为什么放在 DOCUMENT 而非 REVIEW 或专用节点**：DOCUMENT 节点已有"工作流自身变更检测"逻辑，两者同属"工作流元一致性检查"，合并在一处执行，避免分散。规范文件变更频率低，不需要独立节点。

### D5 — PRD 输入路径 + init vs think 说明（BRAINSTORM Step 1）

**决策**：在 BRAINSTORM 第 1 步末尾添加"检测输入类型"表格（需求描述 vs PRD 文档），PRD 路径显式引用 `prd-input-template.md`，且明确 PRD 已充分时跳过第 3 步。同时在"情况 B"中添加对新项目的非阻塞建议：有大量已有代码时优先执行 `/viktor:init`。

### D6 — CONTRACT/REVIEW 单文件逻辑明文化

**决策**：在两个 Skill 的冷启动检测中，补充"只有一个文件时直接告知并使用，无需选择"的明文说明。

## 结果

**正面影响**：
- BRAINSTORM 完成最后一块冷启动检测缺口，全部 6 个主流程节点现均有冷启动保护
- INIT 可放心重复执行，适合项目重构后更新知识地图
- digest 建议每次可见，用户可自主决定整合文档的时机
- references 变更现有追溯机制，减少规范漂移风险
- PRD 输入路径明确，减少 AI 在 PRD 场景下的多余提问

**负面影响/已知限制**：
- BRAINSTORM 增加了前置询问（仅在有历史 spec 时），对全新项目无影响；对有历史 spec 的会话增加一次交互
- references 检测表格是静态列表，新增 reference 文件后需手动维护映射关系

**已知问题（来自 CR）**：
- [NIT] BRAINSTORM Step 1 中"查看 docs/specs/"与冷启动前置步骤存在轻微语义重叠，可在后续迭代中调整措辞
- [NIT] "检测输入类型"表格嵌套在 Step 1 末尾，位置不如独立前置步骤显眼，可在后续重构中提取

## 替代方案

**BRAINSTORM 冷启动 — 不询问，自动检测语义相似度**：通过对比用户输入与已有 spec 标题的语义相似度，自动决定是新建还是更新。否决原因：语义比对可靠性不足，可能产生误判；一次明确询问成本低。

**INIT 幂等 — 自动判断是否需要重新扫描（比较时间戳）**：若 `project-context.md` 最后修改时间 < 最近一次 `git commit` 时间，自动触发重新扫描。否决原因：时间戳比较不可靠（文件可能被触碰但内容未变），且用户需要明确知道触发了重新扫描这一高影响操作。
