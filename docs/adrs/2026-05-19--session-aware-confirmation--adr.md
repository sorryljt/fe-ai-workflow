# ADR-004: 为节点命令引入会话感知冷启动检测机制

**日期**：2026-05-19
**状态**：已接受
**提出者**：Dawson
**关联需求**：会话感知确认机制 + 命令入口修复

## 背景

工作流各节点命令（`/viktor:plan`、`/viktor:code`、`/viktor:cr` 等）在设计上假设用户按顺序执行，但实际使用中出现了两类问题：

1. **命令入口缺失**：`/viktor:context` 和 `/viktor:digest` 的源文件在 `commands/viktor/` 下存在，但 `.claude/commands/viktor/` 中缺少对应入口文件，导致 Claude Code 命令列表无法识别这两个命令。

2. **冷启动行为风险**：用户在新对话中直接执行某个节点命令（如 `/viktor:code`）时，Skill 会静默扫描 `docs/plans/` 并开始执行最近的 tasks.md，存在以下隐患：
   - 用户可能是误触命令，本意是开始新功能
   - 历史 tasks.md 的复选框可能未更新（代码已实现但未标记完成），导致重复实现
   - 多个历史 tasks.md 并存时，Skill 自动取最新的，用户无感知

核心约束：不能把每次执行都变成繁琐的确认弹窗（降低流畅度），但又要防范冷启动时的盲目执行。

## 决策

**我们决定：以当前对话中上游节点的导航卡为信号，区分"在流模式"和"冷启动模式"，仅在冷启动时展示产物列表并请求确认。**

具体规则：
- **在流模式**：对话历史中存在上游节点的完成导航卡（含 `▶ 下一步` 指向本命令）→ 直接执行，零打扰
- **冷启动模式**：对话中无上游信号 → 扫描对应目录下的历史产物，列出状态，请用户选择或重定向

同步修复命令入口缺失：为 `context` 和 `digest` 补充 `.claude/commands/viktor/` 入口文件。

## 方案对比

| 方案 | 优势 | 劣势 | 选择结果 |
|------|------|------|---------|
| 会话感知（对话历史为信号） | 在流时零打扰；冷启动时自动保护；无需持久化状态 | 依赖 Claude 对话历史感知，跨会话需冷启动 | ✅ 选择 |
| 总是确认 | 最安全，绝无误执行 | 每次都要多一步，流程繁琐，破坏连续体验 | ❌ 排除 |
| 不加确认（维持现状） | 最流畅 | 冷启动风险高，历史遗留任务文件可能被误执行 | ❌ 排除 |
| 持久化 session 状态文件 | 跨会话也能感知流程位置 | 引入新的状态管理复杂度，维护成本高 | ❌ 排除 |

**实现架构决策**：各节点 Skill 独立实现检测逻辑，不抽取公共 Skill。原因：Skill 间无真正的调用机制，抽取公共 Skill 实为增加维护耦合；"统一"体现在设计规范和措辞模板一致，而非文件复用。

**风险分级实现**：
- TDD（`/viktor:code`）：风险最高（历史任务文件可能已实现但未标记）→ 总是展示文件列表，全部完成的加 ⚠️ 警告 + 二次确认
- REVIEW / DOCUMENT：中等风险 → 条件确认（检测到未完成任务、已有同名产物、BLOCKING 等情形时触发）
- ANALYZE / CONTRACT：低风险 → 条件确认（仅多文件歧义或覆盖风险时触发）
- CONTEXT / DIGEST / BRAINSTORM：工具/创作节点 → 不加检测

## 结果

**正面影响**：
- 连续执行工作流时体验无变化（在流模式零干扰）
- 冷启动进入任何节点时，用户明确知道将操作哪个历史产物
- `/viktor:context` 和 `/viktor:digest` 正确出现在 Claude Code 命令列表中
- 三端入口（CLAUDE.md / AGENTS.md / workflow.mdc）同步更新，Codex 和 Cursor 行为一致

**负面影响 / 已知问题**：
- 跨会话时（新开对话）即便用户知道自己的意图，也要经历一次冷启动选择
- T005（CONTRACT）和 T006（REVIEW）的冷启动文案未明文说明"单文件时直接使用"，行为是隐含的（NIT，不影响功能）
