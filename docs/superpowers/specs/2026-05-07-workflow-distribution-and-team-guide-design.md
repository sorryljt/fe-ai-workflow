# fe-ai-workflow 分发与团队试点文档设计

**日期**：2026-05-07
**状态**：待确认
**关联需求**：将工作流以 git 方式分发到团队项目，并输出一份用于内部小范围试点的说明文档

> **设计假设**（以下判断来自当前仓库上下文推断，如有不符请指出具体条目）：
> 1. 团队试点优先选用 `git submodule` 作为 workflow 源仓库的接入方式，保持版本可控且便于回滚。
> 2. 业务项目根目录必须物化 `AGENTS.md` / `CLAUDE.md` / `skills/` / `references/` / `commands/` / `.cursor/rules/workflow.mdc`，否则 Claude Code / Codex / Cursor 无法稳定识别。
> 3. Codex 的兼容规则保持无前导 `/` 的 `viktor:*` 文本协议；Claude Code 继续使用 `/viktor:*` 命令式入口。
> 4. 团队试点文档只产出一份主文档，优先放在工作流仓库根目录下的 `docs/team-workflow-guide.md`，用于背景、安装、命令说明与试点说明。
> 5. 安装过程优先通过一个轻量同步脚本完成，不要求团队成员手动复制文件。

## 1. 背景

目前 `fe-ai-workflow` 已经能在 Claude Code 和 OpenAI Codex 下运行，并且通过本地 demo `todo-glass` 验证了 Codex 兼容规则。下一步需要把这套工作流从“单机验证”推进到“团队可试点使用”：

- 团队成员需要能从 git 仓库拉取同一版本的工作流资产
- 业务项目需要自动获得 Claude Code / Codex / Cursor 能读取的入口文件
- 需要一份统一文档，帮助团队成员快速理解这套工作流的背景、安装方式和命令使用方式
- 试点范围要小，便于收集反馈并在正式推广前修正规则

## 2. 目标

**要做的事**：
- [ ] 将 `fe-ai-workflow` 作为独立 git 仓库发布，支持按版本引用
- [ ] 提供一个安装/同步机制，使业务项目能够自动获得工作流入口文件
- [ ] 输出一份单篇团队试点文档，覆盖背景、安装、命令介绍和试点范围
- [ ] 保持 Claude Code 的命令式体验不变，同时保留 Codex 的文本协议兼容

**不做的事**：
- 不在本轮设计复杂的包管理器发布流程
- 不强制团队统一使用同一种 AI 工具
- 不把 workflow 变成依赖远端在线服务的 SaaS
- 不在本轮引入权限系统、埋点平台或管理后台

## 3. 方案对比

| 维度 | 方案 A：git submodule + 同步脚本 | 方案 B：git subtree + 同步脚本 | 方案 C：纯复制安装脚本 |
|------|--------|--------|--------|
| 更新控制 | 强，能固定 workflow 版本 | 中等，目录更像普通代码 | 弱，容易出现手工偏差 |
| 使用成本 | 中等，需要理解 submodule | 低，团队体验更接近普通目录 | 低，安装最简单 |
| 回滚能力 | 强，切换 tag 即可 | 中等，回滚需要额外操作 | 弱，依赖文件覆盖 |
| 适合试点 | 是 | 可以 | 可以，但不适合长期治理 |
| 对工具兼容 | 好，入口文件可物化到项目根目录 | 好，入口文件可物化到项目根目录 | 好，但规范性较弱 |

### 推荐方案：方案 A

推荐 `git submodule + 同步脚本`，原因是：

1. workflow 本身是“版本化规则”，适合用 git tag 精确锁定
2. 小范围试点最重要的是可回滚、可对照、可复现
3. 一旦团队对规则有争议，能快速切换到上一个版本
4. 同步脚本可以把“工具真正要读的入口文件”落到项目根部，避免 submodule 目录本身不被识别的问题

## 4. 选定方案

**选择方案 A：git submodule + 同步脚本**

整体流程是：

1. 团队项目把 `fe-ai-workflow` 作为 submodule 引入到固定路径，例如 `.workflow/fe-ai-workflow`
2. 项目提供一个同步脚本，把 workflow 入口文件复制到项目根目录
3. 之后 Claude Code / Codex / Cursor 读取项目根目录中的入口文件
4. 团队只需要更新 submodule 指针并重新同步，即可升级 workflow 版本

## 5. 技术细节

### 5.1 仓库分发方式

workflow 仓库保持独立，建议通过 tag 发布版本，例如：

- `v0.1.0`
- `v0.2.0`
- `v0.3.0`

业务项目按 tag 或 commit hash 引用，以便锁定试点版本。

### 5.2 安装与同步流程

业务项目侧提供一个同步脚本，职责如下：

- 从 `.workflow/fe-ai-workflow` 读取最新工作流资产
- 将以下文件复制到项目根目录：
  - `AGENTS.md`
  - `CLAUDE.md`
  - `skills/`
  - `references/`
  - `commands/`
  - `.cursor/rules/workflow.mdc`
- 保证这些文件的内容与 workflow 仓库版本一致
- 支持重复执行，避免多次安装产生不一致

### 5.3 平台入口约定

**Claude Code**
- 继续使用 `/viktor:*` 命令式入口
- 读取根目录 `CLAUDE.md`

**OpenAI Codex**
- 使用无前导 `/` 的 `viktor:*` 文本协议
- 读取根目录 `AGENTS.md`
- 不依赖命令面板是否显示 slash command

**Cursor**
- 读取 `.cursor/rules/workflow.mdc`

### 5.4 团队试点文档结构

单篇文档建议命名为 `docs/team-workflow-guide.md`，内容结构如下：

1. 背景
2. 适用范围与试点目标
3. 安装方式
4. 平台差异说明
5. 命令总览
6. 各节点说明
7. 试点建议与反馈入口

文档目标是让团队成员读完后能独立完成一次完整 workflow 体验，而不是只了解概念。

### 5.5 组件边界

这个发布方案可拆成三个独立单元：

- **发布单元**：git tag / submodule / 仓库版本控制
- **同步单元**：把入口文件复制到业务项目根目录
- **说明单元**：单篇团队试点文档

这三个单元可以独立演进，不要求在同一次修改里完全耦合。

## 6. 边界条件与错误处理

| 场景 | 触发条件 | 处理方式 | 用户提示 |
|------|---------|---------|---------|
| submodule 未初始化 | 业务项目未执行 submodule init/update | 提示先初始化 workflow 源仓库 | “workflow 源仓库未拉取，请先初始化 submodule” |
| 同步脚本重复执行 | 已经同步过入口文件 | 幂等覆盖，不报错 | 无 |
| 版本不一致 | 根目录入口文件与 submodule 版本不一致 | 重新同步并提示版本差异 | “检测到 workflow 版本不一致，请重新同步” |
| Codex 输入前导 `/` | 用户在 Codex 中输入 `/viktor:*` | 解释平台差异，提示改用 `viktor:*` | “Codex 中请不要输入前导 /” |
| 团队成员只看 README | 未阅读试点文档直接开始使用 | README 中加简短指引并链接试点文档 | “建议先阅读团队试点文档” |

## 7. 验收标准

- [ ] 业务项目可以通过 git 方式拉取固定版本的 workflow 仓库
- [ ] 一次同步后，Claude Code / Codex / Cursor 能读取各自所需的入口文件
- [ ] Codex 下可通过 `viktor:*` 文本协议或自然语言触发节点
- [ ] Claude Code 下仍可通过 `/viktor:*` 命令式体验使用 workflow
- [ ] 团队试点文档覆盖背景、安装、命令介绍与试点建议
- [ ] 文档读者能在不借助作者解释的情况下完成首次安装和首次试用
- [ ] 同步流程可重复执行，且不会破坏已存在的入口文件
- [ ] 试点范围足够小，便于两周内收集反馈并迭代
